# NFCQSL 卡数据格式

本文件记录 `index.html` 当前实际使用的卡片格式。修改读写代码时，应先检查本文件，避免新代码把旧卡片按另一种格式解释。

## 版本约定

- 当前格式记为 **NFCQSL legacy v1**。
- v1 数据本身没有协议名或版本字段，版本只能由下述 NDEF 结构和 JSON 字段约定识别。
- 已发行的 v1 卡片格式不得被重新定义。需要改变 NDEF 记录布局、字符编码、字段含义或字段类型时，应建立新版本，并让读取端保留对 v1 的兼容分支。
- 新版本应在数据中加入明确的协议标识和版本号；在此之前，不要向 v1 写入器中单独加入一个会被误认为 v1 固有字段的 `version`。

## NDEF 封装与编码

写入端执行：

```js
const message = JSON.stringify(qslData);
await new NDEFReader().write(message);
```

因此，规范的 v1 卡片是一个由 Web NFC 字符串写入方式生成的 **单条 NFC Forum Well-Known Text 记录**（TNF 为 `1`，TYPE 为 `T`/`0x54`）。记录内容为一个紧凑 JSON 文本，字符编码为 **UTF-8**。当前页面的 `<html lang="en">` 还会使 Web NFC 写入 Text 记录的语言标签 `en`。JSON 不依赖空白或对象键顺序；下方顺序只是当前写入器的输出顺序。

当前写入器在写卡前只检查 JSON 文本本身的 UTF-8 长度不超过 **504 字节**，对应代码对 NTAG215 可用空间的假设。该数值不包含 NDEF/TLV 等封装开销，因此它是当前实现的校验规则，不是所有标签都一定能成功写入的容量保证。实际写入仍可能由浏览器或标签拒绝。

## JSON 结构

顶层必须是一个 JSON 对象。v1 的标准字段如下，所有字段值均为 JSON 字符串：

| 字段 | 含义 | 格式或当前行为 |
| --- | --- | --- |
| `cfm` | 确认类型 | 非空时为 `Our QSO` 或 `Your SWL Report`；允许空字符串 |
| `toRadio` | 对方电台呼号 | 自由文本；允许空字符串 |
| `date` | 日期 | HTML date 值，通常为 `YYYY-MM-DD`；允许空字符串 |
| `time` | 时间 | HTML time 值，通常为 `HH:mm`；允许空字符串，不含时区 |
| `freq` | 频率 | 自由文本，页面标注单位为 MHz；允许空字符串 |
| `mode` | 模式 | 自由文本；允许空字符串 |
| `rst` | 信号报告 | 自由文本；允许空字符串 |
| `rig` | 电台设备 | 自由文本；允许空字符串 |
| `pwr` | 功率 | 自由文本；允许空字符串 |
| `ant` | 天线 | 自由文本；允许空字符串 |
| `qth` | 电台位置 | 自由文本；允许空字符串 |
| `op` | 操作员 | 自由文本；允许空字符串 |

页面中的示例值只通过标签说明或 `placeholder` 显示，不属于卡片数据。未填写的字段仍会保留字段名，并以空字符串写入；这不改变 v1 的字段结构和类型。早期写入器曾在部分空字段中自动写入示例默认值，读取器仍须正常显示这些历史值。

当前写入器生成的结构示例：

```json
{
  "cfm": "Our QSO",
  "toRadio": "BG0ABC",
  "date": "2026-08-21",
  "time": "14:30",
  "freq": "14.270",
  "mode": "SSB",
  "rst": "59",
  "rig": "Example Rig",
  "pwr": "10W",
  "ant": "Dipole",
  "qth": "Example QTH",
  "op": "Example Operator"
}
```

线上的实际 JSON 由 `JSON.stringify` 生成，是没有缩进和换行的等价形式。

## 当前读取逻辑

读取端按以下顺序处理卡片：

1. 扫描 NDEF 标签。
2. 将每条记录的 `record.data` 都按 UTF-8 解码。
3. 使用两个换行符连接所有解码结果。
4. 对连接后的完整文本执行 `JSON.parse`，成功后仅格式化展示。

读取端目前不检查 NDEF 记录类型、不校验上述字段，也不检查协议版本。为保证 v1 卡能被稳定读取，写入端应只写一条 UTF-8 Text 记录，且内容只包含一个合法 JSON 对象。虽然解析器会显示额外字段或缺少字段的对象，但这不代表这些变体已成为 v1 标准。

## 兼容性规则

- 修复 UI、样式或展示方式时，不应改变卡内数据格式。
- v1 字段名、类型和含义不可原地复用或改变；尤其不要把字符串字段改为数字。
- 读取器应忽略不认识的附加字段，并允许字段缺失，以便处理历史卡或扩展数据；写入器仍应写全 v1 标准字段。
- 若新需求只能通过不兼容变更实现，应定义带明确协议标识和版本号的新格式，同时以“无版本字段的上述对象”识别 legacy v1。
- 锁卡操作调用 `NDEFReader.makeReadOnly()`，通常不可逆；它不改变数据格式，只改变标签是否还能写入。
